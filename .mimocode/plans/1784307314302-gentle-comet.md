# Fix Turbopack panic in `next dev`

## Problem
`next dev` panics in turbopack's `turbo-tasks-backend` during compilation:

```
inner_of_upper_lost_followers is not able to remove followers TaskId 36
(<DiskFileSystem as FileSystem>::raw_read_dir) from TaskId 70303
(all_server_paths) as they don't exist as upper or follower edges
```

This is a **known Turbopack bug** in Next.js 16.1.6 (see [vercel/next.js#89950](https://github.com/vercel/next.js/issues/89950)). The panic occurs in `aggregation_update.rs` when managing the internal task dependency graph for file system operations.

## Fix

**Option A (recommended): Upgrade Next.js**

Update `next` from 16.1.6 → 16.2.9 (latest stable):

```bash
pnpm update next@latest eslint-config-next@latest
```

Then clear the corrupted cache and restart:

```bash
rm -rf .next
pnpm dev
```

**Option B (fallback if upgrade causes breaking changes): Run dev without turbopack**

Add `--no-turbopack` flag:

```bash
next dev --no-turbopack
```

This bypasses the buggy turbo-tasks-backend entirely. Slower HMR but stable.

## Steps

1. Run `pnpm update next@latest eslint-config-next@latest`
2. Run `rm -rf .next`
3. Run `pnpm dev` to verify the panic is gone
4. If upgrade causes issues, fall back to `next dev --no-turbopack` in `package.json` dev script

## Files to modify
- `package.json` — bump `next` and `eslint-config-next` versions
- Possibly `next.config.ts` if any config changes needed

## Verification
- `pnpm dev` starts without panics and compiles `/` successfully
- Navigate to pages and confirm HMR works
